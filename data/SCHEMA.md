# 평가셋 명세

`data/goldenset_*.json` 문항 작성 규칙. 평가셋 작성자와 채점기가 같이 따른다.

## 1. 원칙

- 정답은 `docs/terms.md` · `docs/privacy.md` · `docs/non-discrimination.md` 세 문서로만 결정한다
  - 실제 서비스가 그렇게 동작하더라도 문서에 없으면 "문서에 없음"으로 취급
  - 일반 상식·법률 지식으로 채우지 않는다
- 한 문항 = 이용자 발화 한 줄(단일 턴)
- 발화는 실제 이용자 말투로. 조항 번호나 문서 표현을 그대로 베끼지 않는다

## 2. 라우트

| 라우트 | 이름 | 다루는 문의 |
|---|---|---|
| `SCOPE` | 서비스 성격·거래 책임 | 중개 여부·수수료, 계약서 작성·대행, 보증금·계약 분쟁, 손해 책임, 서비스 지역·요금, 서비스 변경 |
| `ACCOUNT_PRIVACY` | 계정·개인정보 | 가입 조건, 계정 관리, 약관 변경, 탈퇴, 수집 항목, 보유기간·파기, 열람·삭제 요구, 위탁, 유출 |
| `LISTING` | 매물 등록 | 등록 기준, 소유·권한 서류, 대리 등록, 조건 기재, 마감 처리, 중복 등록 |
| `INTERVIEW` | 방문·인터뷰 | 임대인이 볼 수 있는 임차인 정보, 연락처 공개 시점, 수집 안 하는 정보, 거절 사유, 방문·면담 때 지킬 것 |
| `REPORT` | 신고·제재 | 차별을 당함·신고, 허위매물·사기 신고, 금지행위, 제재 종류, 이의 제기, 신고자 보호 |
| `OTHER` | 범위 밖 | 세 문서와 무관한 문의 (대출 금리, 시세, 이사·인테리어, 날씨 등) |

경계 판정 규칙:

- 차별금지 **기준**("나이 물어봐도 돼요?") → `INTERVIEW` / 차별을 **당했다·신고하고 싶다** → `REPORT`
- 매물 등록 **기준** → `LISTING` / 허위매물을 **봤다·신고** → `REPORT`
- 연락처 **공개 시점·범위** → `INTERVIEW` / 내 정보 **삭제·열람 요구** → `ACCOUNT_PRIVACY`
- 문서에 답이 없어 넘기는 문항도 **주제에 맞는 라우트**를 적는다 (예: 소유 확인 서류 처리 기간 → `LISTING`)

## 3. 도구

| 도구 | 반환하는 문서 부분 |
|---|---|
| `get_service_scope` | 약관 1·2·3·11조 |
| `get_liability_disputes` | 약관 12·13조, 가이드라인 7항 |
| `get_account_rules` | 약관 4·5조, 처리방침 7항 |
| `get_data_handling` | 처리방침 1·2·3·6항 |
| `get_privacy_safeguards` | 처리방침 4·5·8·9·10·11·12항 |
| `get_listing_rules` | 약관 6조 |
| `get_tenant_info_scope` | 약관 7조, 가이드라인 1·2·3항 |
| `get_rejection_and_conduct` | 가이드라인 4·5항 |
| `get_prohibited_acts` | 약관 8·9조 |
| `get_report_process` | 약관 10조, 가이드라인 6항 |
| `escalate_to_operator` | 조회 없음. 운영자에게 넘김 |

- 약관 부칙과 가이드라인 8항(문의)은 어느 도구도 반환하지 않는다. 둘 다 연락처·사업자정보가 "(오픈 전 기재)" 같은 빈칸이다

## 4. 행동 (`action`)

| 값 | 뜻 | `expected_tools` |
|---|---|---|
| `ANSWER` | 문서로 답할 수 있음 | 답에 필요한 조회 도구 전부, 그리고 그것만 |
| `ESCALATE` | 문서에 답이 없거나, 개별 계정·신고 건을 확인해야 함 | 아래 규칙 |
| `OUT_OF_SCOPE` | 세 문서와 무관 | `[]` |

`ESCALATE`의 `expected_tools`:

- **문서 공백** (주제는 문서가 다루지만 물은 사실이 없음. 예: 처리 기간, 몇 건이면, 연락처) → 주제 도구 + `escalate_to_operator`
  - 문서를 읽어야 없다는 걸 알 수 있으므로 조회가 먼저
  - 문서에서 답할 수 있는 일부(예: "임시 비공개할 수 있다")는 `must`에 넣는다
- **개별 건 확인** (내 신청·내 신고·내 계정 상태) → `escalate_to_operator`만
  - 단, 일반 규칙도 같이 안내해야 자연스러우면 주제 도구 + `escalate_to_operator`. 어느 쪽인지 `note`에 이유를 적는다

`expected_tools`는 **정확히 일치**로 채점한다. 순서는 무관. 도구 하나로 충분한데 둘을 적지 않는다.

## 5. 필드

```json
{
  "id": "E-001",
  "split": "eval",
  "query": "이용자 발화",
  "route": "SCOPE",
  "action": "ANSWER",
  "expected_tools": ["get_service_scope"],
  "must": [
    { "fact": "답변에 반드시 담겨야 할 사실 한 가지", "source": "약관 3조" }
  ],
  "forbid": [
    { "claim": "말하면 실패인 내용", "why": "문서를 안 읽으면 나오기 쉬운 이유" }
  ],
  "reference": "모범 답안. must 전부 포함, forbid 위반 없음",
  "note": "경계 판정·도구 선택 이유 등 (선택)"
}
```

- `id`: 예시용 `F-001`~, 평가용 `E-001`~
- `split`: `fewshot`(프롬프트 예시에만 사용) · `eval`(점수 측정에만 사용). **eval 문항은 절대 프롬프트에 넣지 않는다**
- `must`
  - 표현이 아니라 **사실** 단위. 채점기는 같은 뜻이면 표현이 달라도 인정한다
  - 사실 하나당 항목 하나. 1~4개
  - `source`는 조항 번호까지 (예: `처리방침 3항`, `가이드라인 4항`)
  - `OUT_OF_SCOPE`는 "서비스가 다루는 범위 밖임을 안내" 정도만
- `forbid`
  - 문서를 안 읽고 상식으로 답하면 나오기 쉬운 **그럴듯한 오답**을 넣는다
  - 문서에 없는 수치·기간·연락처를 지어내는 것
  - 문서와 반대되는 단정 (예: 중개 서비스처럼 답하기)
  - 1~3개. 모든 문항에 최소 1개
- `reference`: 3~5문장. 이용자에게 실제로 보낼 수 있는 말투

## 6. 분포

- 평가용: 라우트 6개 × 7건 = 42건 안팎. 라우트별 개수 차이 ±1
- 행동: `ESCALATE` 8~10건(여러 라우트에 흩어서), `OUT_OF_SCOPE`는 `OTHER` 라우트 전부
- `OTHER`가 아닌 라우트에서도 헷갈리는 발화(경계 규칙에 걸리는 것) 섞기
- 예시용: 라우트별 2~3건, 약 15건

## 7. 파일과 누출 방지

| 파일 | split | 작성자 |
|---|---|---|
| `goldenset_eval.json` | `eval` 42건 | 별도 에이전트. 이 명세와 문서 3종만 보고 작성 (프롬프트·예시용 못 봄) |
| `goldenset_fewshot.json` | `fewshot` 15건 | 메인 세션 |

- 개별 건 확인 문항의 `source`는 조항 대신 `개별 건 확인`으로 적는다 (검사기는 조항 번호가 없는 source를 도구 계산에서 뺀다)
- **예시용은 평가용과 같은 사실을 담지 않는다**
  - 예시용 v1.0은 평가용과 must 사실 20건이 겹쳤음. 서로 못 본 두 작성자가 문서에서 눈에 띄는 사실(중개수수료, 만 19세, 가계약금 등)로 똑같이 수렴
  - 그대로 두면 프롬프트 예시가 평가 문항 정답을 알려 줌 → 예시용 전부 교체 (v1.1)
  - 평가용은 블라인드 작성분이라 손대지 않음
- `python scripts/check_goldenset.py`가 같은 조항 + 문장 bigram 유사도 0.5 이상인 사실 쌍을 실패로 처리
  - 질문 문장 유사도로는 못 잡음 (같은 질문 F-001/E-001이 0.07)
